# Full OneBusAway app in Flutter, as an SDK

Goal: mirror the functionality of the OneBusAway iOS app (`../ios`) in Flutter.
Every feature lives in a package that another app can embed. The app in this
repo is a thin shim, in the same way `Apps/OneBusAway` is a shim over
`OBAKit` / `OBAKitCore`.

## Package layout

| Package | iOS counterpart | Flutter? | Contents |
|---|---|---|---|
| `packages/onebusaway` (exists) | `OBAKitCore/Network`, `Models/REST` | pure Dart | Full OBA REST client, Regions API client, Obaco/sidecar client, polyline codec |
| `packages/obakit_core` (new) | rest of `OBAKitCore` | pure Dart | `ObaAppConfig`, `ObaCoreApplication`, regions service, user data store (bookmarks, groups, recents, stop preferences, alarms, read alerts), settings, deep-link routers, search manager, formatters, walking time, analytics protocol, feature flags, surveys logic. Platform access goes through interfaces (`KeyValueStore`, `LocationProvider`, `PushServiceProvider`) |
| `packages/oba_arrivals` (exists) | embeddable arrivals card | Flutter | Unchanged API; reused by the stop page |
| `packages/obakit` (new) | `OBAKit` | Flutter | `ObaApp` root widget, `ObaScope`, theme, l10n, and every screen. Each screen is also exported for embedding on its own. Ships the `shared_preferences` and `geolocator` adapters |
| `packages/obakit_trip_planner` (new) | `otpkit` | Flutter | OTP client (GraphQL, falling back to REST 1.x) and trip planner UI |
| `lib/` (rewritten) | `Apps/OneBusAway` | Flutter | `main.dart` builds an `ObaAppConfig` and runs `ObaApp`. Nothing else |
| `packages/oba_arrivals/example` | – | Flutter | The current UCSD Student Life embedding demo moves here |

Dependencies point one way: `lib → obakit → {obakit_core, oba_arrivals, obakit_trip_planner} → onebusaway`.

## Decisions

- **Map:** `flutter_map` (pure Dart, no API key, runs on iOS, Android, macOS and web). The tile URL and attribution are part of `ObaAppConfig`, so a host can swap providers.
- **State:** `ChangeNotifier` / `ValueNotifier`, as in `oba_arrivals`. No state-management dependency is forced on hosts.
- **Navigation:** the map-panel experience is the target (full-screen map and a draggable sheet with Home / Recent / Bookmarks). The classic tab bar UI is not ported.
- **Strings:** `gen-l10n` ARB files in `obakit`, English first, then the 12 other locales the iOS app ships (it has 13 `.lproj` directories including English: ar, es, fil, fr, it, ko, pl, pt-BR, ru, vi, zh-Hans, zh-Hant) converted from the `.strings` tables where keys correspond.
- **Tests:** real fixtures copied from `../ios/OBAKitTests/fixtures`. Logic is tested without widgets wherever possible.

## Cross-cutting requirements

- **Embedding parts is the main use case.** The first consumer is the UCSD Student Life app, which will take individual pieces (a stop page, a nearby-stops card, the map, the trip planner), not the whole app. Every screen is a plain widget that needs only an `ObaScope` ancestor. Navigation goes through an `ObaNavigator` the host can override, and the map coordinator is optional.
- **Accessibility is a hard requirement (WCAG 2.1 AA).** Text scales to 200% without loss of content, colour pairs meet contrast minimums in light and dark, status is never conveyed by colour alone, every control has screen-reader semantics, the map has a non-visual alternative, targets are at least 48dp, and reduce-motion and high-contrast settings are honoured. Widget tests run Flutter's accessibility guidelines through a shared harness. A dedicated audit pass covers all packages, including `oba_arrivals` and `obakit_trip_planner`, before the final review.

## Feature map

Ported:

- Regions: fetch, cache, bundled fallback, auto-select by location, manual picker, experimental/inactive toggles, custom regions.
- Map: stop pins with direction and route type, zoom threshold with a "zoom in for stops" pill, user location, map type, route shapes and vehicles for the selected stop, dropped pin, weather button.
- Home sheet: nearby stops with next departures, recent stops, bookmarks, alarms, alerts, explore, settings and more.
- Search: route, stop number, vehicle ID, address (through a pluggable geocoder), bookmark matches.
- Stop page: time and route-grouped modes, earlier departures, walk-time divider, departure-type filter, per-stop route filter and sort, service alerts, bookmark, refresh, schedules, nearby stops, walking directions, report problem.
- Trip page: stop list with collapsed runs, vehicle position, adjacent block trips, trip map, bookmark, ghost-bus and vehicle problem reports.
- Schedules for a stop and a route.
- Bookmarks: stop and trip bookmarks, groups, reorder, pin, sort by group or distance.
- Recent stops, service and agency alerts with read state, agencies list.
- Settings and More screens, onboarding (welcome, location, region), fare payment link, donations link, contact us, credits.
- Deep links (`onebusaway://` and sidecar universal-link formats).
- Trip planning through OTP.
- Weather, vehicle search, surveys and alarm creation through Obaco.
- Analytics protocol with a no-op default.

Exposed as an interface only (a host supplies the implementation, as iOS does with `pushServiceProvider`):

- Push notifications. Alarms and service-alert pushes need a device token and APNs/FCM credentials; the alarm UI is shown only when a `PushServiceProvider` is configured.
- Address search (`PlaceSearchProvider`); a Nominatim-backed default ships in `obakit`.

Not ported, because they are Apple-platform extensions with no Flutter equivalent inside an SDK: Live Activities, home-screen widgets, the watch app, App Intents/Siri/Spotlight/Visual Intelligence, HealthKit speed sync, voice search, TipKit, Look Around.

Deferred (large, self-contained, and off by default or experimental on iOS): on-demand/GTFS-Flex, bikes and scooters layer, vehicle position estimation, trip suggestions, proximity (geofence) alerts, the legacy-app data migration, the SQLite stop cache.

## Phases

1. **API layer** (two agents in parallel, `packages/onebusaway`): the remaining `api/where` endpoints and models; Regions, Obaco and polyline.
2. **Core** (`packages/obakit_core`).
3. **UI scaffold** (`packages/obakit`): application object, scope, theme, l10n, adapters, navigation shell, map.
4. **Screens** (parallel agents on separate directories): stop + schedules + trip + reporting; bookmarks + recents + alerts + agencies; regions + onboarding + settings + more; search + home sections.
5. **Shim and platforms**: rewrite `lib/`, move the demo, permissions and URL schemes for iOS, Android and macOS; run on the iOS simulator and an Android emulator.
6. **Extras**: trip planner package, weather, surveys, alarms, deep links, translations.
7. **Review and docs**: code review pass, README and AGENTS.md updates, CI.

## Status

As of 2026-11-25:

- Phases 1 to 5 are done. Phases 6 and 7 are in progress: the trip planner, weather, surveys, alarms and deep links exist, and the README, AGENTS.md and CI updates are written.
- Device verification is done on the iOS simulator and an Android emulator, using `integration_test/walkthrough_test.dart` against live servers.
- Translations are in progress. English is complete; the other locales are being converted from the iOS `.strings` tables.

Known partial behaviours:

- Region-wide alerts are sampled from the arrivals at bookmarked, recent and nearby stops, not read from the GTFS-realtime alerts feed.
- Schedule times use the device time zone, not the agency's.
- The alarm flow was only tested with alarms unavailable (no `PushServiceProvider`), so the create and remove paths have not run on a device.
- A Flutter framework semantics null-check bug is mitigated (see `packages/obakit/lib/src/shell/sheet_navigator.dart`) pending a Flutter upgrade that contains the fix for flutter/flutter#186178 (upstream change #192146).
- The "Compact" density and "Show stop labels" settings are hidden, because the UI doesn't implement them yet.
